第一层是**流程编排**。入口 skill 只是个「薄路由」——先把你的原话钉死成 canonical research query（存到 research/runs/<vault_tag>/query.md，之后每一步、每个子 agent 都只读这份原文），然后按阶段逐个加载 step skill。README 特别强调了这么做的原因：长流水线最怕「上下文腐烂」导致悄悄漏步骤，把每一步的程序只在真正执行时载入上下文，是对抗这个问题的工程手段。

第二层是**对抗式验证**。这是它最有技术壁垒的地方。四个批评家（dialectic/depth/width/instruction）并行攻击草稿，分别负责「漏掉的反证」「能填的浅坑」「语料支持但草稿忽略的角落」「跟用户问题原子项的结构错配」。批评家挑出的毛病只有能塞进小块 Edit hunk 的才允许改，其余升级为结构性 issue。跑完还有 cite-checker 抽样复查「引文-句子绑定」是否成立，以及出货时的撤稿扫描（对每个被引 DOI 重新查一遍，昨天发的撤稿今天就抓到）。还有一个很聪明的「来源独立性审计」：五家媒体转载同一份新闻稿，只算一票——这直接击穿了「syndication = consensus」这个深度研究里最常见的自欺。

第三层是**知识资产化**。大多数研究工具是一次性的：报告出来，其它全扔。Hyperresearch 把每个抓到的来源都落进 vault——纯 Markdown + YAML frontmatter，SQLite 只是可重建索引。它还带溯源面包屑（--suggested-by 把来源串成从种子出发的有根树，provenance lint 规则抓断裂的孤岛）、PageRank 中心度、质量分（来源类型 + 抓取效用 + 引用权威 + PageRank 合成的 composite quality_score，撤稿论文直接地板到近零）。生命周期上，笔记走 draft → review → evergreen，老化的走 stale → deprecated → archive，防止 vault 变成半读网页的垃圾场。

**技术栈**方面：Python 3.11–3.13（明确不支持 3.14）。抓取用 crawl4ai，PDF 用 pymupdf，学术检索打八个源头。模型分层明确写在 subagent roster 里：fetcher / source-analyst / loci-analyst / cite-checker 默认 Sonnet，draft-orchestrator / synthesizer / 四个 critic / patcher / polish-auditor 默认 Opus，而且这些不是硬编码，能在 .hyperresearch/config.toml 里按 profile 覆盖。还有个 browser-fetcher 用 Claude-in-Chrome 驱动你本机真 Chrome 去啃抓取升级队列。

**规模杠杆**分两个维度：「tier」决定跑哪些步骤（light 5 步 / full 全 16 步 / dissertation 章节化 300–450 来源），「gear」决定源量、深度预算、字数目标（premier 档 100–130 源，full 档 55–80 源）；另有 levers 决定报告的「语气体裁」（teach / survey / analyze / advocate）和 rabbithole 深度，注意 levers 会渲染成 role-scoped shim 贴进子 agent 提示词，让批评家跟着体裁走——但 cite-checker 和出货闸门**不接收 shim**，验证环节永不因模式而软化。

**开放获取抢救**这块是给论文档次的用户准备的：DOI 论文抓不到全文时，依次尝试 Unpaywall 已知的 PDF、落地页、Europe PMC 结构化全文（JATS 解析，比 pymupdf 处理双栏 PDF 更干净），候选必须同时满足「比你已有的多」和「超过 oa_min_full_text_chars」两个门槛才被接受，避免一个仓库记录页冒充全文。默认 contact_email 为空，所以 Unpaywall 被跳过，只有 Europe PMC 开放子集生效——要开启得填真实邮箱。

**坦白的边界**：它不能替你判断哪些来源重要；不能抓你没登录的付费墙内容；运行在 Anthropic 模型上，成本随 tier/gear/语料规模线性膨胀；lint 闸门只能抓结构性失败，不能保证事实准确。

4. github/spec-kit:
   star: 135831  语言/技术: Python 3.11+, uv, pipx, specify-cli（PyPI 包）, CLI 交互工具, Markdown 模板 / Slash 命令与 Agent Skills, Git, GitHub Issues, AI 编程代理（GitHub Copilot、Claude、Codex CLI、Command Code、GitHub Copilot CLI 等 30+）
   项目简介: Spec Kit 是 GitHub 开源的一套「规格驱动开发」（Spec-Driven Development，SDD）工具箱，核心理念是“先定义要造什么，再让 AI 动手造”。它把过去写完就扔的规格文档变成可执行的“一等公民”：你先写项目宪法（原则）、再写需求规格、再写技术方案、再拆任务，最后由 AI 编程代理按序执行并收敛验证。它不绑定任何单一模型或 IDE，宣称兼容 30+ 种 AI 编程代理，并提供扩展、预设、角色包等机制做深度定制。对天天跟 AI 结对写代码、但被“AI 乱改代码/需求跑偏/无法复现”折磨的开发者来说，这是个相当对症的流程管理器。
   亮点: 把“规格”变成可执行资产：规格不再是一次性脚手架，而是直接驱动实现，甚至能反向校验代码是否真的实现了需求; 提供一条完整可重复的 SDD 流水线：constitution（立宪）→ specify（写规格）→ plan（技术方案）→ tasks（拆任务）→ implement（执行）→ converge（收敛验证），并配 clarify / analyze / checklist 三个可选质量关卡; 跨代理、跨模型中立：不锁死某一家 AI 编程助手，宣称支持 30+ 集成；同一套命令在 slash 命令模式与 Agent Skills 模式下均可使用; 可扩展架构设计清晰：Extensions（加能力）、Presets（改模板/术语）、Bundles（角色化打包）、项目级 Overrides 四层优先级，模板运行时解析、命令安装时落盘，冲突时高优先级胜出; 附带两条“非功能开发”工作流：bug 扩展做 assess → fix → test（防止 AI 从 bug 报告直接跳到瞎打补丁），assess 扩展做 intake → research → define → shape → decide（给一个想法开一张 go / needs-clarification / kill 的诊断书）; CLI 自带自我管理：specify self check / self upgrade（支持 --dry-run、--tag 钉版本、超时控制），并支持 --non-interactive 的无键盘 CI/Agent 场景
   详细报告: Spec Kit 想解决的问题很朴素但很痛：在 AI 编程代理越来越能写代码的今天，真正的瓶颈已经从“写代码”变成了“说清楚要写什么、并且验证它真的写对了”。传统开发里规格文档只是脚手架，代码一开工就被丢进垃圾桶；Spec Kit 反过来，把规格抬成可执行的核心资产，让规格去直接生成和约束实现。

它的工作方式是一条带编号的流水线。第一步是“立宪”：用 /speckit.constitution（skills 模式下写作 speckit-constitution，Codex CLI 与 Command Code 用 $speckit-*，GitHub Copilot CLI 用 /agents 选择或直接对话）为项目建立治理原则，比如代码质量、测试标准、用户体验一致性、性能要求。这是每个项目一次性的动作。第二步 specify：只讲“做什么、为什么”，不碰技术栈。第三步 plan：这时候才把技术栈与架构（例如 Vite + 原生 HTML/CSS/JS + 本地 SQLite）交底。第四步 tasks：把方案拆成可执行任务清单。第五步 implement：代理按清单干活。第六步 converge：拿代码库去对照 spec/plan/tasks，把没做完的部分追加成新任务，循环 implement + converge 直到报告 Converged。这条闭环里的关键价值在于“可验证性”——不是让 AI 自我感觉良好地说“我做完了”，而是有客观的规格做验收基准。

除了主干流程，它还挺务实地配了三个可选的补丁式命令：clarify（在 plan 之前把没说清的地方问清楚，前身叫 /quizme）、analyze（跨产物一致性与覆盖度分析，跑在 tasks 之后、implement 之前）、checklist（生成自定义质量清单，作者称之为“给英文写的单元测试”，用来检查需求是否完整、清晰、一致）。另外还有个 taskstoissues 命令，能把生成的任务清单直接转成 GitHub issue，把 AI 工作流接进真实的需求追踪系统。

扩展体系是它“不止是个模板仓库”的地方。README 明确给了四层优先级：项目本地 Overrides（.specify/templates/overrides/）> Presets（.specify/presets/templates/）> Extensions（.specify/extensions/templates/）> Core（.specify/templates/）。模板在运行时自上而下解析取第一个命中；扩展/预设的命令文件则在安装时（specify extension add / specify preset add）写入代理目录，比如 .claude/commands/。多个预设或扩展撞名时高优先级胜出，移除后次高优先级自动恢复。这个设计等于给企业团队留了“在不 fork 上游的前提下做私有规范”的口子。

安装侧，它通过 uv 或 pipx 分发 specify-cli，要求 Python 3.11+ 和 Git，Windows/macOS/Linux 均可。初始化命令 specify init my-project --integration copilot 会按选定代理铺开对应目录结构。对 CI 或无法发送方向键的伪终端场景，可用 --non-interactive；往非空目录初始化则配合 --force。自管理方面，specify self check 只读探测新版本，specify self upgrade 默认不弹确认直接升级（对齐 pip install -U / npm update 的习惯），还支持 --dry-run 预览、--tag 钉版本（含 dev/alpha/beta/rc 后缀），并能自动识别 uv tool 与 pipx 安装形态；对 uvx 临时运行和源码检出会给出路径化提示而不是硬跑安装器，升级子进程超时可用 SPECIFY_UPGRADE_TIMEOUT_SECS 控制。

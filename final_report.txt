核心工作流分三块。第一块是 Voice 工作区，有三个标签页：From audio（从一段音频克隆音色，3 秒可用，5–15 秒效果更好）、By design（不靠参考音频，而是用年龄、口音、音高、风格、表达方式等指令“设计”出一个音色）、Convert（语音到语音的音色转换）。第二块是 Dubbing（视频配音）：从文件或 URL 导入，支持字幕导入、可选 YouTube 登录，然后走“转写 → 翻译 → 说话人保持 → 合成 → 导出”的链路；编辑界面把播放控制叠在视频上并做背景虚化，波形和带时间戳的转写合并成一个紧凑编辑面，波形可拖动平移、点击定位；翻译语言与 ISO 代码联动，选 Auto 会清掉之前的语言和方言；转写条目按“可编辑文本 / 时序与状态 / 音色控制”三行分组；还有 Glossary 术语表和时间轴问题标记，方便译后复查。第三块是长音频：Audiobook Script 编辑器、多角色配音脚本、EPUB/PDF 导入、分章渲染、导出 .m4b；casting board 用图标式音色卡片，支持把卡片拖到某个说话人上，或从菜单挑音色。

2. MG1937/ASC:
   star: 1284  语言/技术: Python, Deflate 比特流解析（不完整 inflate）, Huffman 查找表构建, DEX 字节码格式, R8 编译器优化行为分析, O(1) 指令定位原语, 内存内动态 DEX 重建, CLI 工具（支持 --gui / --threads）
   项目简介: Droid ASC 是一个把“编译产物当数据库直接查”的 Android 反编译引擎（Black Hat Europe Arsenal 议题配套工具）。传统反编译器（如各类 APK 反编译工具）打开一个巨型 APK 时，习惯先无脑全量解压、再把所有 DEX 塞进内存、建一大堆全局索引和交叉引用表，结果动辄吃掉几个 G 内存、等上几十分钟，就为了后面搜索快一点——而 APK 本身其实已经是高度结构化的数据，这波预处理属于典型的“给已经排好队的数据再排一次队”。Droid ASC 反其道而行：零预处理、无状态，按需毫秒级定位代码。官方演示在一个 352MB 的商业 APK 上：全局交叉引用搜索 1.79 秒、目标类反编译 177 毫秒、峰值内存仅 141MB。对做 Android 逆向、恶意样本分析、SDK 审计的安全打工人来说，属于“终于不用先去泡杯咖啡再回来等反编译器”的存在。
   亮点: 零预处理 + 无状态：不做全局索引、不做全量解压，把 APK 当只读数据库按需查询，内存占用从“几个 G”降到 141MB 级别; 直接在 Deflate 比特流里“探针式”读取：构建稠密 Huffman 查找表，只提取核心元数据，不碰无关数据块，绕开完整 inflate 这个最耗时环节; 把 R8 编译器的优化行为武器化：利用 compiler 的确定性常量重定位与指令去重留下的高聚集物理布局，做闪电级跨 DEX 代码搜索; O(1) 指令定位原语：把裸字节码 offset 映射回方法时不需要建重型映射表，实现常数时间的方法解析; 命中即最小重建：只抽取目标字节码及其依赖，在内存里动态重建一个最小且自洽的 DEX，立刻反编译，绝不“顺手把整个 APK 展开”; 实测战绩：352MB 商业 APK 上全局交叉引用搜索 1.79s、目标类反编译 177ms，这个数字对逆向工程师来说是降维打击
   详细报告: 先说说这个项目到底在骂谁。所有做过 Android 逆向的人都经历过这个流程：拿到一个几百 MB 的 APK，扔进反编译工具，然后……等。等它把压缩包全量解压（inflate），等它把几十上百个 DEX 全部塞进内存，等它建立庞大的全局索引、交叉引用表、方法映射表。工具的理由是“这样后面搜索快”，但 Droid ASC 的作者直接把这套逻辑定性为反常识：APK 编译产物本身就是高度结构化的数据，现代反编译器却完全不利用这一点，反而在已经结构化的数据上重建一个臃肿的代码关系数据库，属于重复劳动 + 资源浪费。作者的灵魂发问是：当我能直接从 APK 里毫秒级抽出任意代码关系时，这种预处理还有存在价值吗？

于是工程实现上走了完全相反的路线——不驱动反编译器去做重预处理，而是把编译产物当成一个只读数据库来查询，做一个无状态、零开销引擎，按需抽取和搜索。具体的技术拆解有这么几层：

第一层是绕过全量解压。APK 内部是 Deflate 压缩的，传统做法是先 inflate 成完整字节流再解析。Droid ASC 直接在这个 Deflate 比特流里面做探针（probing），构建稠密的 Huffman 查找表，只把核心元数据抠出来，完全不触碰无关的数据块。这相当于“我不拆快递盒，直接用探针感知里面装的是啥”。

第二层是吃 R8 编译器的红利。它分析了 R8 的优化特性，特别是确定性的常量重定位（deterministic constant relocation）和指令去重（instruction deduplication）——这两个优化会让同类内容在物理布局上高度聚集。作者把这个“编译器行为”反过来当武器用，实现极快的跨 DEX 代码搜索。这是整个项目最聪明的地方：别人眼中的编译器优化产物，在这里变成了索引结构本身。

第三层是映射问题的消解。搜到裸字节码 offset 之后，怎么知道它属于哪个方法？传统做法是建表映射。Droid ASC 设计了一个 O(1) 指令定位原语，做到常数时间的方法解析，不需要重型映射表。

第四层是按需反编译。一旦命中目标，它只抽取那一段特定字节码以及它的依赖，在内存里动态重建一个最小、自洽的 DEX，然后立刻对这个“迷你 DEX”做反编译。这样既不用加载全部内容，也不用为整个 APK 付出代价。

使用层面很直接，pip install droidasc 或从源码安装后，全局就有 droidasc 命令，也可以 python main.py。子命令有三个：getclass（定位目标类 → 在内存中抽出一个 DEX → 反编译）、getmanifest（解出 AndroidManifest.xml 并打印为 XML）、findrefs（跨所有 DEX 条目查找字符串 / 类型 / 方法 / 字段的代码引用）。常用参数包括 -o 输出文件、--threads 线程数、--class 指定类、--fuzzy-class 模糊匹配类名、--gui 图形界面。示例命令如 droidasc getclass app.apk Lcom/poc/Main; -o Main.java 或 droidasc findrefs app.apk method notify --class MainActivity --fuzzy-class -o method_refs.txt，对逆向工程师来说学习成本几乎为零。

性能数据是它最大的卖点：352MB 商业 APK，全局交叉引用搜索 1.79 秒，目标类反编译 177 毫秒，仅 141MB 内存。作者的原话是把编译产物当只读数据库、零预处理运行，从而让反编译器回归本质——不再是臃肿的索引工具，而是一个闪电般快速、按需反编译的引擎。
